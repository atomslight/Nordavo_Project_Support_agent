## Constraints

  No new frameworks, services, vector DB, RAG or agent libraries.
- Keep be/ (API, state, config) and ai/ (prompts, model calls, policy) separate.
  ai/ never makes HTTP calls to the helpdesk or reads env vars.
- Prompts live in ai/prompts.py as plain constants, filled with .replace()
  (never .format(), because of JSON braces). Static rules and the FAQ go first,
  per-ticket values last. The FAQ is kept exactly as given and goes whole into
  the decision prompt for every ticket.
- First move the language prompt into ai/prompts.py (pure move, own commit), then
  extract the shared provider call (own commit), tests green before and after.
- Ticket text is untrusted data. Redact payment details before storage,
  prompts and logs.
- Client rules: answer only from the FAQ; refunds, disputed charges,
  cancellations, contract changes, GDPR/AVG, security incidents, legal threats
  and churn threats always go to a human; no card or IBAN in replies or logs;
  reply in the customer's language; handoff notes in English.
- A wrong reply is worse than a handoff, but handing off everything fails too.
- Provider limits: Gemini 3.5 Flash-Lite free = 15 requests/min, 500/day, 250K
  tokens/min. Groq qwen/qwen3.8-27b free = 30 requests/min, 8K tokens/min, 200K
  tokens/day. A ticket costs about 2 requests. Add a pacer in the shared provider
  call (max 14 Gemini requests per 60s). A Gemini 429 waits for retry-after and
  retries; fall back to Groq only on real errors or repeated 429s.

## Design to plan around (challenge it if the code says otherwise)
Per ticket: redact -> language (existing) -> policy gate (code) -> one decision
call -> validator (code) -> save decision -> send -> log.

Gate and decision:
- The gate passes forced_action, priority_floor and triggered_rules into the
  prompt, and code enforces them again afterwards. Floors: P1 for security and
  legal; P2 for refunds, disputes, cancellation, contract, GDPR/AVG, churn.
  Compare priorities numerically, not as strings.
- close_allowed is set by code only (empty body or a matched spam rule).
- Language "unknown" -> handoff. The API accepts only nl/en/de, so send a default
  (nl) and list it under assumptions.
- The decision JSON: reason first, then category, priority, action, faq_ids,
  faq_evidence, draft_reply or handoff_note, confidence (logged, never used to
  decide).
- The prompt includes the P1-P4 and category definitions from the brief, the
  customer plan (never offer Plus-only features to Basis), draft rules (exact
  Dutch menu names, promise nothing outside the FAQ, hand off if only part of a
  request is covered) and what a handoff note must contain (what the customer
  wants, plan, rule that fired, suggested next step).
- "Unsure" means: no valid FAQ evidence, validator failure, unknown language, or
  a mixed request the FAQ only partly covers. Record this under Decisions.

Validator (any failure becomes a handoff, which still ends as success):
- action matches fields; faq_ids exist; each faq_evidence item is found in the
  FAQ text after whitespace normalisation; no card or IBAN in any output;
  Dutch menu names match the FAQ; draft language equals ticket language via
  LanguageAnalyzer.

Ledger (new ticket_decision table; leave ticket_state alone):
- Columns: ticket_id, status, decision_json, error, attempts, updated_at.
- Three statuses: pending, success, failed.
- Save decision_json before the POST. A timeout never becomes failed; it stays
  pending.
- Rerun rules: success -> skip. pending without decision_json -> redo the
  decision. pending with decision_json -> GET /tickets/{id} first; if handled,
  mark success, else send the stored decision with no new model call. failed ->
  retry up to 3 attempts; 400/422 stay failed.
- 503 retries (nothing was saved), 429 waits Retry-After, 409 counts as success
  and is never resent.
- The API is the source of truth. A row "success" for a ticket the API lists as
  open is stale (practice reset): clear it. `--reset` calls POST /practice/reset
  and clears the ledger.

CLI and logs:
- `nordavo run` is dry by default and `--send` posts. A dry run does not touch
  the ledger. `nordavo eval` runs decisions on the 10 examples with no POST and no
  ledger, scores language, category, priority and action separately plus the cited
  FAQ, and never puts the examples in the prompt.
- At the end of a run print counts per status and exit non-zero if any failed
  remain.
- One JSON log line per ticket in logs/: id, action, category, priority, gate
  rules, validator result, provider/model, tokens, latency, retries, status,
  http status, error type. No ticket text.
- Add a verifier or a separate draft call only if the eval shows a need.
